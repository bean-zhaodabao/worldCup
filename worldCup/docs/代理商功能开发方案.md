# 代理商功能开发方案

> 版本：v0.2（核心需求已确认）
> 编写日期：2026-10-23
> 本次更新：确认佣金按流水计、每代理独立比例；代理端只读；复用现有移动端；新增阿里云短信通知
> 关联系统：worldCup（足球彩票系统）
> 适用范围：用户端 uni-app `kaiyun/`、管理端 `admin/`、uniCloud 后端 `kaiyun/uniCloud-alipay/`

---

## 一、结论先行（推荐方案）

客户已确认的核心诉求有三件事：

1. **代理商只能查询**自己推广的用户数据与订单数据，**不能创建用户、不能充值、不能停用用户**；
2. **移动端有一个简单的只读管理后台**，复用现有 App；
3. **用户下注成功后，通过阿里云短信通知后台配置的手机号**。

同时确认：**佣金按流水计算，每个代理独立设置佣金比例**。

建议在现有系统上做**角色扩展**，不另起一套系统：

| 项目 | 确认做法 |
|------|---------|
| 代理身份 | 复用 `users` 集合，新增 `role = "agent"`，用独立字段存代理资料与佣金账户 |
| 用户归属 | 用户新增 `agentId` 字段；**仅管理员创建/分配/转移**，代理端只读 |
| 代理层级 | 一期只做**单层代理**（代理 → 直属用户），不做总代/二级分佣 |
| 代理权限 | **只读**：查用户、查订单、查佣金；无任何写操作 |
| 移动端 | **复用现有 uni-app**，新增 `pages-agent` 分包，登录后按角色跳转代理工作台 |
| PC 管理端 | 新增「代理商管理」「佣金结算」「短信通知」菜单，用户管理增加所属代理字段 |
| 佣金 | **按流水返佣**：`佣金 = 下注额 × 代理独立比例`；比例由管理员为每个代理单独配置 |
| 短信 | 下注成功后异步发送阿里云短信到后台配置的手机号，失败不影响下单 |
| 数据统计 | 代理端只做「概览 + 用户 + 订单 + 佣金」4 个模块，不做复杂报表 |
| 数据口径 | 所有查询服务端强制按 `agentId` 过滤，代理之间数据完全隔离 |

> 代理端严格只读，连「申请佣金提现」也暂不开放；佣金由管理员在 PC 端确认并线下结算。若后续希望代理自助提现，再单独开放。

## 二、现状评估

### 2.1 现有架构

| 端 | 技术栈 | 关键位置 |
|---|--------|---------|
| 用户端 | uni-app (Vue3)，App / H5 / 小程序 | `kaiyun/pages/`、`kaiyun/pages.json` |
| 管理端 | Vue3 + Element Plus，PC Web | `admin/src/views/`、`admin/src/router/index.js` |
| 后端 | uniCloud（阿里云）云函数 + 云数据库 | `kaiyun/uniCloud-alipay/cloudfunctions/`、`database/schemas/` |
| 用户端调用 | `uniCloud.callFunction` 直连云函数 | 例：`pages/login/login.vue` 调 `user-auth` |
| 管理端调用 | HTTP URL 化 + axios | `admin/src/utils/request.js`，如 `/admin-user` |

### 2.2 可复用的能力

- 登录 / Token：`users` 集合 + `generateToken` / `verifyToken`，24 小时有效。
- 用户体系：`role`（user/admin）、`type`（retail/collector）、余额、冻结余额、状态。
- 订单体系：`orders`（订单主表）+ `order-items`（玩法明细、赔率快照），状态含 pending/won/lost/settled/refunded。
- 钱包：`wallet-logs` 流水、`withdrawals` 提现、管理端审核。
- 管理端框架：路由、菜单、请求拦截、操作日志、Element Plus 组件。
- 移动端框架：tabBar、登录、订单列表/详情、个人中心，可直接复用样式。

### 2.3 需要特别注意的现状问题

这些问题会直接影响代理功能的**安全性和准确性**，建议一并处理：

1. **管理端接口没有校验角色**
   现有所有 `admin-*` 云函数只调用 `verifyToken`，但 `verifyToken` 不判断 `role`，普通用户 Token 也能调用管理端接口（例如重置任意用户密码、查看全部订单）。代理功能上线前必须修复：所有 `admin-*` 增加 `role === 'admin'` 校验。

2. **下单接口没有限制角色**
   `user-order` 同样只校验 Token，管理员/代理 Token 也能下单。代理账号应禁止下注，需加角色限制。

3. **密码明文存储**
   当前 `users.password` 是明文，Token 签名也依赖明文密码。短期可不改，但属于风险项；建议在代理功能之后单独排期做哈希迁移。

4. **报表是「全表加载后内存汇总」**
   `admin-report`、`admin-order` 会一次性取全量订单。代理端数据量虽然更小，但也不能沿用这种方式，新增接口必须使用分页 + 聚合查询 + 索引。

5. **结算入口不止一个**
   自动结算在 `sync-jczq`，手工中奖判定在 `admin-play`，赛事结算在 `admin-settle`。佣金计算不能硬编码到某一个入口，建议用**独立、幂等的佣金任务**统一处理。

## 三、角色与权限模型

### 3.1 角色定义

| 角色 | `role` | 说明 | 登录入口 |
|------|--------|------|---------|
| 散户 | `user` + `type=retail` | 有钱包，下注校验余额 | 用户端 |
| 收单账户 | `user` + `type=collector` | 不校验余额，可为负 | 用户端 |
| 代理商 | `agent` | 只读查看自己名下用户/订单/佣金 | 用户端（登录后跳代理工作台） |
| 管理员 | `admin` | 全局管理 | PC 管理端 |

> 代理**不参与下注**，代理账号不进入用户端赛事/订单页面。

### 3.2 权限矩阵

| 功能 | 代理 | 管理员 |
|------|------|--------|
| 创建下属用户 | ❌ | ✅ 可指定代理 |
| 查看下属用户列表/详情 | ✅ 仅自己名下 | ✅ 全部 |
| 重置下属用户密码 | ❌ | ✅ 全部 |
| 启用/停用下属用户 | ❌ | ✅ 全部 |
| 给下属用户充值/调额 | ❌ | ✅ 全部 |
| 查看下属用户订单 | ✅ 仅自己名下 | ✅ 全部 |
| 查看佣金明细/汇总 | ✅ 仅自己 | ✅ 全部 |
| 申请佣金提现 | ❌（一期不开放） | — |
| 确认佣金/标记已支付 | ❌ | ✅ |
| 修改佣金比例 | ❌ | ✅ 每个代理独立设置 |
| 转移用户归属 | ❌ | ✅（记日志） |
| 配置短信手机号/模板 | ❌ | ✅ |
| 修改赛事/玩法/赔率/结算 | ❌ | ✅ |

> 代理端所有接口只提供 `list` / `detail` / `summary` 这类查询 action，不提供任何写接口。

### 3.3 用户归属规则

- 用户表新增 `agentId`，表示**当前归属代理**。
- 订单表新增 `agentId` 快照，表示**下单时归属代理**。
- 用户创建、代理分配、代理转移**全部由管理员在 PC 端完成**，代理端无写权限。
- 用户转移代理后：
  - 历史订单的佣金仍归**下单时**的代理（快照原则）；
  - 新订单归新代理；
  - 转移操作只允许管理员执行并写操作日志。
- 代理被停用后：
  - 不能登录；
  - 名下用户仍可正常下注；
  - 已产生佣金管理员仍可查看、确认和线下结算。
- 统计口径：
  - 用户数按 `users.agentId` 当前归属统计；
  - 订单、流水、佣金按订单 `agentId` 下单时快照统计；
  - 用户转移后，代理名下用户数与历史订单数可能不一致，这是预期行为。

## 四、业务流程

### 4.1 代理开户

```
管理员在 PC 端创建代理账号
  → 设置用户名/密码、佣金比例、状态
  → 系统生成唯一代理编号 agentCode（如 AG0001）
  → 代理用同一登录页登录
  → 识别 role=agent，跳转移动端代理工作台
```

### 4.2 推广用户绑定（仅管理员操作）

由于代理端只读，一期用户归属只走管理员：

```
管理员在 PC 端创建用户
  → 选择所属代理（可选）
  → 服务端写入 agentId / agentCodeSnapshot / bindTime
  → 记录操作日志

已有用户变更代理
  → 管理员在用户管理执行「转移代理」
  → 更新 users.agentId
  → 历史订单的快照不变
  → 记录操作日志
```

二期可选：代理分享邀请码/二维码，用户自助注册时填写邀请码，服务端写入 `agentId`。由于当前系统没有手机号验证，自助注册需要额外的防刷措施，建议二期再做。

### 4.3 用户下注、短信与佣金产生

```
用户下注
  → user-order 创建订单
  → 订单写入 agentId / agentRate 快照（来自用户当前归属代理）
  → 写入一条短信任务（sms-tasks，异步）
  → 返回下单成功（短信失败不影响订单）

短信任务（定时/队列）
  → 读取后台配置的手机号、签名、模板
  → 调用阿里云短信 SendSms
  → 成功/失败写 sms-logs，失败按策略重试

比赛结算，订单进入 settled / refunded
  → 佣金任务扫描已结算订单
  → 生成佣金记录（幂等，一单一记录）
  → 管理员在 PC 端确认 → 可结算
  → 管理员线下打款并标记已支付
```

### 4.4 佣金结算（代理端只读）

```
佣金任务生成 pending 记录
  → 管理员在 PC 端查看/核对
  → 确认入账（available）
  → 线下打款给代理
  → 管理端标记「已支付」
```

> 系统不接支付，佣金结算是「管理员线下打款 + 管理端标记」。代理端只展示待确认/可结算/已支付金额，不提供申请提现按钮。

## 五、数据模型设计

### 5.1 `users` 集合扩展

```jsonc
{
  "_id": "xxx",
  "username": "agent001",
  "password": "******",
  "role": "agent",                    // 枚举新增 agent
  "type": "retail",                   // 代理不使用；下属用户仍为 retail/collector
  "status": "active",

  // ===== 下属用户字段（role=user 时）=====
  "agentId": "代理用户ID",             // 当前归属代理，null 表示无代理
  "agentCodeSnapshot": "AG0001",       // 绑定时快照，便于展示/排查
  "bindTime": "2026-10-23T00:00:00Z",  // 绑定时间

  // ===== 代理字段（role=agent 时）=====
  "agentCode": "AG0001",               // 唯一代理编号，用于展示/对账
  "commissionRate": 2.5,               // 佣金比例，单位：百分比（2.5 表示 2.5%），每个代理独立
  "commissionBalance": 0,              // 已确认、待线下结算的佣金
  "paidCommission": 0,                 // 已线下支付的佣金
  "totalCommission": 0,                // 累计产生的佣金
  "parentAgentId": null,               // 预留：上级代理（二期多级分佣）
  "remark": "",

  "balance": 0,
  "frozenBalance": 0,
  "createTime": "2026-10-23T00:00:00Z"
}
```

**说明：**

- 不新建 `agents` 表，避免登录、鉴权、用户管理两套体系；代理资料直接挂在 `users` 上。
- `commissionRate` 用百分比数值，前端展示时加 `%`，避免 0.025 / 2.5 的歧义。
- `agentCode` 需要唯一索引；建议由服务端按 `AG + 4位序号` 生成，冲突时重试。

### 5.2 `orders` 集合扩展

```jsonc
{
  "agentId": "代理用户ID",        // 下单时用户归属代理快照，null 表示无代理
  "agentRate": 2.5,               // 下单时佣金比例快照
  "commissionStatus": "none",     // none=未处理 / pending=已生成待确认 / done=已入账 / void=已冲销 / skipped=不参与
  "commissionAmount": 0,          // 本单产生的佣金
  "commissionRecordId": "",       // 关联佣金记录ID
  "commissionTime": null          // 佣金处理时间
}
```

**为什么下单时快照？**

- 用户中途换代理、代理比例调整时，历史订单归属和佣金比例不混乱；
- 佣金任务不需要反查用户当前归属，性能更好；
- 对账时可以直接按订单追溯；
- 代理端订单列表/详情也按订单 `agentId` 快照过滤：用户转移后，历史订单仍归原代理，新订单归新代理。

> 如果客户希望「按结算时的最新比例」计算，也可以改为结算时读取代理当前比例。默认建议下单时快照，规则更稳定。

### 5.3 新增 `agent-commission-records`（佣金记录）

```jsonc
{
  "_id": "xxx",
  "agentId": "代理用户ID",
  "agentName": "agent001",
  "userId": "下单用户ID",
  "userName": "user001",
  "orderId": "订单ID",
  "orderNo": "WC20261023xxxx",
  "orderBetAmount": 100,          // 订单下注额快照
  "orderWinAmount": 0,            // 订单返还额快照（含本金）
  "baseType": "turnover",         // 计佣基数类型，一期固定 turnover
  "baseAmount": 100,              // 计佣基数
  "rate": 2.5,                    // 佣金比例快照（%）
  "amount": 2.5,                  // 佣金金额
  "status": "pending",            // pending=待确认 / available=可结算 / paid=已支付 / void=已冲销
  "settleBatchId": "",            // 结算批次
  "orderSettledAt": "2026-10-23T00:00:00Z",
  "createTime": "2026-10-23T00:00:00Z",
  "confirmTime": null,
  "payTime": null,
  "remark": ""
}
```

**唯一索引：`agentId + orderId`**，保证同一订单只生成一条佣金记录，任务重复执行不会重复计佣。

### 5.4 新增 `agent-commission-settlements`（佣金结算批次）

代理端不申请提现，由管理员按批次线下结算：

```jsonc
{
  "agentId": "代理用户ID",
  "agentName": "agent001",
  "recordIds": ["佣金记录ID"],
  "recordCount": 10,
  "amount": 100,
  "periodStart": "2026-10-01T00:00:00Z",
  "periodEnd": "2026-10-31T23:59:59Z",
  "status": "pending",             // pending=待打款 / paid=已打款 / cancelled=取消
  "createTime": "2026-10-23T00:00:00Z",
  "operatorId": "",
  "operatorName": "",
  "paidTime": null,
  "remark": "",
  "payVoucher": ""                 // 线下打款凭证（可选，图片URL/备注）
}
```

### 5.5 新增 `agent-wallet-logs`（代理佣金流水）

```jsonc
{
  "agentId": "代理用户ID",
  "type": "commission",            // commission=佣金确认入账 / paid=线下支付 / adjust=调整
  "amount": 2.5,                   // 正数入账，负数出账
  "balanceAfter": 102.5,
  "recordId": "佣金记录ID",
  "settlementId": "结算批次ID",
  "remark": "",
  "operatorId": "",
  "operatorName": "",
  "createTime": "2026-10-23T00:00:00Z"
}
```

> 不复用 `wallet-logs`，避免代理佣金和用户下注/中奖流水混在一起，报表和对账更清晰。

### 5.6 索引建议

| 集合 | 索引 | 用途 |
|------|------|------|
| `users` | `username` 唯一 | 登录、创建用户查重 |
| `users` | `agentCode` 唯一（稀疏） | 代理编号 |
| `users` | `agentId + status + createTime` | 代理查名下用户 |
| `users` | `role + status` | 登录 |
| `orders` | `orderNo` 唯一 | 订单号 |
| `orders` | `userId + createTime` | 用户订单 |
| `orders` | `agentId + commissionStatus + createTime` | 佣金任务扫描 |
| `orders` | `status + settleTime` | 结算/对账 |
| `order-items` | `orderId`、`playId` | 订单明细/按玩法统计 |
| `agent-commission-records` | `agentId + orderId` 唯一 | 佣金幂等 |
| `agent-commission-records` | `agentId + status + createTime` | 代理佣金列表/汇总 |
| `agent-commission-settlements` | `agentId + status + createTime` | 结算批次 |
| `agent-wallet-logs` | `agentId + createTime` | 流水 |

> 上线前先检查历史数据是否有重复 `username` / `orderNo`，否则唯一索引可能创建失败。

## 六、佣金规则设计（已确认：按流水）

### 6.1 规则与配置

**核心规则（已确认）：**

```
佣金 = 订单下注额 × 该代理的独立佣金比例
```

- 每个代理在创建/编辑时单独设置 `commissionRate`；
- 比例按下单时快照写入订单（`agentRate`），后续调整比例不影响历史订单；
- 只对**已最终结算**的订单计佣；
- 退款、删除、未结算订单不计佣。

配置项：

| 配置项 | 取值 | 默认 | 说明 |
|--------|------|------|------|
| `agentCommissionEnabled` | true/false | true | 总开关，关闭后不产生新佣金 |
| `agentDefaultRate` | 百分比 | 2.5 | 新建代理时的默认比例（每个代理可单独改） |
| `agentCommissionConfirm` | auto/manual | manual | 自动确认/管理员确认 |
| `agentFeatureStartAt` | 时间 | 上线时间 | 只处理该时间之后的订单，避免历史订单被追溯计佣 |

配置写入现有 `system-config` 集合，管理端「系统配置」页维护。代理比例本身存在 `users.commissionRate`，不在全局配置里。

### 6.2 计佣公式与示例

```
佣金 = 订单下注额 × 代理比例
```

示例：

| 用户下注 | 代理比例 | 订单结算状态 | 佣金 |
|---------|---------|-------------|------|
| 100.00 | 2.5% | 已结算（输） | 2.50 |
| 100.00 | 2.5% | 已结算（赢，返还 200） | 2.50 |
| 100.00 | 2.5% | 赛事取消退款 | 0 |
| 100.00 | 2.5% | 订单被删除 | 0 |
| 100.00 | 2.5% | 未结算 | 0（等结算后再算） |

> 流水返佣的特点：无论用户输赢，代理都按流水拿佣金。若后续客户端希望改为「按净盈亏」或「阶梯比例」，属于二期规则变更，需要重新评估。

### 6.3 计佣排除规则

以下订单**不产生佣金**：

- `deleted = true`（管理端逻辑删除）；
- `status = refunded`（赛事取消退款）；
- `status` 不是最终结算状态（pending/won/lost 未最终 settled）；
- 下单时间早于 `agentFeatureStartAt`；
- 用户 `agentId` 为空；
- 代理比例为 0 或佣金开关关闭；
- 代理自己的账号（代理不允许下注）；
- 测试账号（可增加 `isTest` 标记）。

### 6.4 幂等与重算

- 佣金任务按 `agentId + orderId` 唯一索引写入，重复执行只成功一次；
- 订单结算结果被修改（手工改判、退款）时：
  - 佣金记录状态为 `pending`：直接更新金额或冲销；
  - 已 `available` 但未结算：生成反向调整记录；
  - 已 `paid`：生成调整记录，在下期结算中抵扣；
- 管理端提供「重算佣金」按钮，按代理 + 时间范围重跑，所有操作写日志。

### 6.5 结算与支付

```
订单结算 → 佣金记录 pending
  → 每日任务汇总（T+1）
  → 管理员确认（或自动）→ available，增加代理 commissionBalance
  → 管理员线下打款
  → 管理端标记已支付 → paid，累加 paidCommission
```

- `pending` 不计入可结算余额，避免退款/改判导致超发；
- `available` 才会出现在管理端「待打款」列表；
- 代理端只展示金额和状态，不提供提现/确认操作；
- 所有余额变更写 `agent-wallet-logs`，并用原子 `inc` 更新。

### 7.1 统一约定

- 返回结构沿用现有：`{ code: 0, data, message }`，错误 `code != 0`。

## 八、短信通知方案（阿里云）

### 8.1 目标与流程

**需求：** 用户下注成功后，给后台配置的手机号发送短信。

```
用户下单成功
  → 订单落库
  → 写入 sms-tasks（异步任务，不阻塞下单）
  → 返回下单成功

sms-job 定时任务（每分钟）
  → 取待发送任务
  → 调用阿里云 SendSms
  → 成功：写 sms-logs，任务置 success
  → 失败：按退避策略重试（1 分钟 / 5 分钟 / 15 分钟，最多 3 次）
  → 超过重试：置 failed，管理端可手动重发
```

**关键原则：**

- 短信发送**不能影响下单**，失败只记录，不回滚订单；
- 同一订单只通知一次，任务用 `orderId + type` 唯一索引去重；
- 手机号、签名、模板全部后台可配，不写死在代码里；
- AccessKey Secret 只存在服务端，管理端只显示掩码。

> 默认为异步发送，正常情况下 1 分钟内到达；如果业务要求「下单后立即收到」，可改为下单后同步调用（增加几十到几百毫秒耗时，失败仍不影响订单），但高并发时更推荐异步。

### 8.3 阿里云短信接口

**实现方式：**

- 当前模板只使用 `name` 一个变量，`TemplateParam = {"name":"用户名"}`。

### 8.7 发送策略与限流

- 默认「每笔订单都发」；
- 支持配置 `minAmount`，低于阈值不发，控制成本和打扰；
- 支持 `dailyLimit`，超过后任务置 `skipped` 并记录；
- 同一订单只发一次，重试不重复计费；
- 多个接收号码时，阿里云按号码分别计费；
- 如果每天订单量很大，建议后续增加「按小时汇总」或「只发大额订单」模式。

### 8.8 异常处理

| 情况 | 处理 |
|------|------|
| 短信服务未配置/关闭 | 任务置 `skipped`，不影响下单 |
| 手机号格式错误 | 任务置 `failed`，日志记录，管理端可改配置后重发 |
| 阿里云返回 `isv.SMS_SIGNATURE_ILLEGAL` | 签名未审核/已失效，提示管理员 |
| `isv.SMS_TEMPLATE_ILLEGAL` | 模板未审核/变量不匹配，提示管理员 |
| `isv.BUSINESS_LIMIT_CONTROL` | 触发频控，退避重试 |
| `isv.AMOUNT_NOT_ENOUGH` | 余额不足，记录并告警 |
| 网络超时 | 退避重试，最多 3 次 |
| 云函数超时 | 任务保持 `pending`，下轮继续 |

## 十一、关键实现要点

### 11.1 鉴权与越权防护

在新增函数中统一封装：

```js
async function verifyAgent(db, token) {
  const user = await verifyToken(db, token)
  if (!user || user.role !== 'agent') return null
  // 可选：校验 status=active
  return user
}
```

每个接口都必须：

- 用 Token 中的 `_id` 作为代理身份，**不信任前端传的 agentId**；
- 查询用户/订单前先做归属校验；
- 分页参数做上限（如 `pageSize <= 100`）；
- 禁止代理调用管理端函数。

### 11.2 订单写入代理快照

修改 `user-order/index.js` 下单逻辑：

```js
const userRes = await db.collection('users').doc(user._id).get()
const u = userRes.data[0]
const agentId = u.agentId || null
const agentRate = agentId ? await getAgentRate(agentId) : 0
```

订单新增字段：

```js
agentId,
agentRate,
commissionStatus: agentId ? 'none' : 'skipped'
```

> 代理自身禁止下单：在 `user-order` 入口增加 `if (user.role !== 'user') return fail('无下注权限')`。

### 11.3 佣金任务

- 独立云函数 `agent-commission-job`；
- 通过 `config.json` 配置定时触发器（参考 `sync-jczq/config.json`）；
- 用 `commissionStatus` 做游标，避免每次全表扫描；
- 单次处理上限 + 循环分页；
- 失败记录到日志，支持重试；
- 管理端「重算」复用同一套计算函数。

> 注意：现有 `admin-play` 手工判定会把订单置为 `won` / `lost`，`admin-settle` 再置为 `settled`。佣金任务以 `settled` 为最终态；如果实际运营中 `won` / `lost` 已经是终态，需要在任务中兼容，避免漏算。建议统一由赛事结算收口，减少多入口状态不一致。

### 11.4 短信任务实现

- 下单成功后写入 `sms-tasks`，用 `orderId + type` 唯一索引去重；
- 独立云函数 `sms-job`，通过 `config.json` 配置定时触发器（每分钟）；
- 每次取 `status=pending` 且 `nextRetryAt <= now` 的任务，单批 20~50 条；
- 发送成功：任务 `success`，写 `sms-logs`；
- 发送失败：`attempts++`，按 1/5/15 分钟退避，超过上限置 `failed`；
- 管理端可手动重发失败任务；
- 发送前统一校验：开关、手机号、模板、每日上限、金额阈值；
- 日志中手机号脱敏，完整号码只在配置中保存。

### 11.5 统计接口性能

- 用户列表的累计下注/中奖：用聚合 `match + group`，按当前页 userIds 聚合；
- 工作台概览：按时间范围 + `agentId` 聚合，不要拉全量订单；
- 订单列表：先分页查订单，再批量查 `order-items` 和赛事，避免 N+1；
- 所有查询走索引字段；
- 数据量再大时，增加 `agent-user-stats` / `agent-daily-stats` 汇总表，由佣金任务顺带更新（二期）。

### 11.6 操作日志

以下操作必须写 `operation-logs`：

- 创建代理、修改比例、重置代理密码、启停代理；
- 管理员创建用户时指定代理、转移用户归属；
- 佣金确认、重算、冲销、结算批次、标记已支付；
- 短信配置变更、测试发送、手动重发。

日志字段沿用现有：`adminId`、`adminName`、`action`、`targetType`、`targetId`、`detail`、`beforeData`、`afterData`、`createTime`。

## 十二、安全与风控

| 风险 | 措施 |
|------|------|
| 代理越权查其他代理数据 | 服务端强制 `agentId = token._id`，所有 userId/orderId 二次校验 |
| 普通用户调用管理接口 | 修复所有 `admin-*` 的 `role === 'admin'` 校验（P0） |
| 代理调用下注接口 | `user-order` 限制 `role === 'user'` |
| 代理越权写数据 | 代理端只实现查询 action，不实现创建/充值/启停/提现接口 |
| 佣金重复发放 | `agentId + orderId` 唯一索引 + 状态机 |
| 佣金超发 | 只对已结算订单计佣；退款/删除自动冲销；pending 不可结算 |
| 短信 AccessKey 泄露 | 只存服务端；RAM 最小权限；不写前端/Git/日志；Secret 掩码 |
| 短信被刷 | 每日上限、金额阈值、订单唯一索引、同一订单只发一次 |
| 手机号泄露 | 日志脱敏；只有管理员可查看/修改完整号码 |
| 密码明文 | 列为技术债，建议后续哈希迁移；至少接口不返回密码 |
| 登录暴力破解 | 增加登录失败次数限制/验证码（建议与代理功能一起做） |
| 数据导出泄露 | 一期不做导出；如需要，仅管理员可用并记日志 |

## 十三、兼容性与数据迁移

### 13.1 兼容性

- `role` 枚举新增 `agent`，现有 `user/admin` 逻辑不受影响；
- `users` 新增字段都有默认值，老数据无需回填；
- `orders` 新增字段对老订单为 `undefined`，佣金任务通过 `createTime >= agentFeatureStartAt` 过滤；
- `user-auth` 改造后，普通用户登录返回结构只多字段，不破坏现有前端；
- 管理端用户列表仍只查 `role=user`，代理不会混入用户列表；
- 现有结算、钱包、提现逻辑不改；
- 短信是新增旁路能力，不配置/关闭时对下单无影响。

### 13.2 上线步骤

1. 备份数据库；
2. 创建新集合与索引；
3. 更新 schema（`users`、`orders`）并部署；
4. 部署新增/修改的云函数；
5. 配置 `system-config` 默认值；
6. 配置 `agent-commission-job`、`sms-job` 定时器；
7. 在阿里云申请并审核签名/模板，配置短信参数；
8. 创建测试代理 + 测试用户，跑通「分配用户 → 下注 → 短信 → 结算 → 佣金 → 线下结算」；
9. 灰度：先开 1 个代理，观察 1~2 天；
10. 全量开放。

### 13.3 历史数据处理

- 历史订单不补佣金（通过 `agentFeatureStartAt` 控制）；
- 如需给现有用户分配代理，管理员批量操作，写日志；
- 不修改历史订单的 `agentId`，避免追溯纠纷。

## 十七、风险与建议

1. **短信模板审核是当前最大外部依赖**
   阿里云对短信签名/模板审核较严，涉及博彩/彩票/下注类词汇可能被拒。建议先申请签名和模板，用中性文案，审核通过后再联调；代码实现不依赖审核结果，可先用测试号码跑通。

2. **现有管理端鉴权漏洞必须优先修**
   这是独立于代理功能的 P0 安全问题，建议无论代理功能是否上线都尽快修复。

3. **代理只读是明确边界**
   代理端不实现任何写接口，避免后续需求蔓延。若以后要开放创建用户/充值/提现，需要重新做权限、风控和对账设计。

4. **佣金任务要独立、幂等、可重算**
   现有结算入口多，不要把佣金逻辑塞进 `sync-jczq` 或 `admin-play`，否则后续改判/退款很难对账。

5. **统计接口不要沿用全表加载**
   代理端用户量可能持续增长，必须从第一版就用聚合 + 索引 + 分页。

6. **短信量按订单量线性增长**
   如果每天订单量很大，短信费用和打扰都会上升，建议保留金额阈值/每日上限配置，必要时改为汇总通知。

7. **多级代理是二期的大坑**
   一旦引入多级分佣，需要处理层级、比例拆分、跨级结算、代理关系变更，工作量至少翻倍。一期务必锁定单层。

8. **建议先做灰度**
   先给 1~2 个代理使用，验证「用户归属、数据口径、佣金规则、短信到达率」四件事，再全量开放。
